# 🧠 La philosophie du challenge

Ce challenge est fortement inspiré par les principes de **Clean Code** de Robert C. Martin (Uncle Bob).

Mais l'objectif n'est pas de mémoriser des règles.

L'objectif est de développer un **sens du code**.

> Reconnaître un mauvais code est une chose.
> Savoir pourquoi il est mauvais et savoir le transformer progressivement en meilleur code en est une autre.

L'apprentissage reposera donc sur une boucle permanente :

```text
Comprendre
    ↓
Observer
    ↓
Coder
    ↓
Tester
    ↓
Identifier les problèmes
    ↓
Refactorer
    ↓
Mesurer
    ↓
Documenter
    ↓
Recommencer
```

Le code devra être considéré comme quelque chose qui évolue.

On ne cherche donc pas la perfection immédiate.

On cherche à construire un système capable d'évoluer sans devenir progressivement ingérable.

## 3. Clean Architecture

La Clean Architecture sera progressivement introduite lorsque les problèmes de séparation des responsabilités et de dépendances deviendront suffisamment concrets.

L'objectif sera de comprendre :

```text
Presentation
     ↓
Application
     ↓
Domain
     ↓
Infrastructure
```

et surtout la règle fondamentale :

```text
Les détails dépendent des politiques.
Les politiques ne dépendent pas des détails.
```

L'objectif n'est pas de créer une architecture complexe.

L'objectif est de créer une architecture qui permet au logiciel de **changer**.

# 🧹 La règle du refactoring

Le code fonctionnel n'est pas automatiquement du bon code.

Une fonctionnalité peut fonctionner tout en étant :

* difficile à comprendre ;
* difficile à tester ;
* fortement couplée ;
* dupliquée ;
* fragile ;
* difficile à modifier.

Nous chercherons donc régulièrement à appliquer :

```text
Make it work
     ↓
Make it clean
     ↓
Make it better
     ↓
Keep it maintainable
```

Le but n'est jamais de refactorer pour le plaisir.

Chaque refactoring doit répondre à un problème réel.

# 🎓 Règles personnelles du challenge

## 1. Comprendre avant de copier

Je ne veux pas simplement copier du code trouvé sur Internet ou généré par une IA.

Je dois pouvoir expliquer :

* pourquoi ;
* comment ;
* quelles alternatives existent ;
* quels sont les compromis.

---

## 2. L'IA est un assistant, pas un pilote automatique

L'IA peut être utilisée pour :

* expliquer ;
* proposer ;
* challenger ;
* générer un exemple ;
* analyser du code ;
* suggérer un refactoring.

Mais la décision finale doit être comprise et validée par moi.

```text
IA propose
   ↓
Je comprends
   ↓
Je vérifie
   ↓
Je décide
   ↓
J'implémente
```

---

## 3. Mesurer plutôt que supposer

Pour la performance :

```text
Hypothèse
   ↓
Benchmark
   ↓
Modification
   ↓
Benchmark
   ↓
Comparaison
```

Pas :

> "Cette solution semble plus rapide."

Mais :

> "Cette solution est plus rapide parce que la mesure montre X."

---

## 4. Documenter les décisions importantes

Une décision d'architecture importante doit laisser une trace.

```text
Pourquoi avons-nous choisi cette solution ?
```

La réponse doit pouvoir être retrouvée plus tard.

---

## 5. Laisser le code plus propre qu'avant

Chaque intervention doit essayer de respecter :

> **Leave the code cleaner than you found it.**

Pas nécessairement parfait.

Simplement meilleur.
